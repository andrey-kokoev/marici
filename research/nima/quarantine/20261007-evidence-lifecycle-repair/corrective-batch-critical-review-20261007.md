### R1 — High evidence-integrity risk: stale success survives failed reruns (F4)

The repair is not consistently applied across the batch. Steps 5–10 write a
success receipt only after their checks, but do not invalidate an existing one
when a preceding required check raises. Three repaired legacy entry points
have the same lifecycle.

**Reproduction:** copy each actual existing pass receipt to an isolated
owner-local temporary directory; redirect only its output path; inject an
exception at the first `require` call or the `verify` function; execute the
actual `main`. All nine failures propagated, and all nine previous pass files
survived byte-identically. The source and live receipt files were unchanged.

**Distinction:** this is not the old false-zero-exit defect. Required failures
now raise. Nor does the test show that the current live mathematical receipts
are false. It shows that a consumer cannot treat the mere continued presence
of `status: pass` as evidence that the latest attempted run succeeded. A
consumer that requires the matching successful execution avoids this trap;
that condition must be enforced, not presumed.

**Positive control:** the step-1 matrix checker replaces pass with fail and
returns 1 for a false predicate, and removes the old receipt before an
unexpected verification failure (`check_tick_to_square_realization.py:146–154`).
Steps 2–4 also explicitly unlink their output at startup (lines 18, 18 and 17
of their respective checkers). This is not a claim that every receipt,
including the separate step-1 regression report, has a correct lifecycle.

Required repair is a consistent failed-run invalidation/current-run binding,
with this test repeated. No production checker or receipt was repaired during
this review.
