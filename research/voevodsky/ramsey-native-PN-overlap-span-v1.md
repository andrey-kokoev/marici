# Native witnessed PN overlap spans

## Input policy before choosing an overlap

The input schema is the complete set of independently constructed valid chart/eligible-face **port records**, not selected span answers. Each record retains the base P chart, optional reader prefix, actual PN source/target packets, phase frames, full five-coordinate permutation, all references and the two-M law-domain data. The source API validates these records before any pair or triple is chosen.

`RamseyNativePNOverlapSpan.agda` defines the literal policy admitting exactly these supplied full records. Geometry/PN validity is runtime bound to the source; the kernel does not parse JavaScript or infer physical source admission from a string. This policy is explicit and independent of the requested overlap/composition.

## Actual native constructor

For charts a,b the common index type contains one geometric face and both chart-indexed PN permit certificates. Native P retains the two complete input records, P over the common-domain type forms the span, and E selects a certified common index. Both source and target legs are recovered as actual native premises, with their separate law domains retained. No span or composition package is seeded.

The result is a higher WG witnessed partial span. It is not a P/N motion changing roles and does not turn incompatible C/M assignments into one physical role field.

## Composition on the declared common domain

A triple index contains one shared face and the three permits. It uses **the same middle certificate** in the AB and BC legs. The native middle-seam theorem identifies the entire middle port package and input derivation, not just its face or a scalar observation.

A further native P package retains the AB, BC and AC selected-span histories and the full three-port source. The declared source/target face cells commute. The direct AC observation does not erase the AB/BC route or middle packet, and the proof does not identify differently structured whole packages.

This is composition on the stated triple common domain, not on every pair of pairwise-nonempty spans. A more general fiber-product composition with merely equal faces and separately supplied middle witnesses would need its own compatibility cell; it is not assumed here.

## Empty intersections and countercontrols

The concrete source-bound example uses four role charts with C sets {0,2}, {0,1}, {1,2}, {0,3}. The first three have nonempty pairwise PN domains but no common triple face. The last two have disjoint domains. The kernel proves these emptiness statements and separately constructs the native empty P-family. It cannot select an E index or compose a fabricated triple there.

For the nonempty first/second/fourth triple, all native composition/source-retention cells are instantiated with quoted actual port records. Runtime controls also cover all 24 P markings: 48 eligible input ports, 72 source transfers, all pair/triple intersections and middle-source comparisons.

Lost-port extension, empty-pair selection, false triple composition, altered middle source, erased outside C2 and a dropped fifth coefficient coordinate are rejected. These controls preserve the earlier total-domain no-go rather than bypassing it.

## Scope and next gate

This proves actual native higher packages under the declared validated-port policy, not a total PN gauge transformation, physical role-changing path, simultaneous assembly, full four-face descent, whole-space admission or Ramsey forcing. The source policy and runtime PN binding are not replaced by an assertion that a mathematical intersection is already native.

The broader chart-descent question must still sew the four-face cover with appropriately typed role/law-domain data and any additional operation cells. Empty or incompatible overlaps must remain explicit; neither the direct AC leg nor common geometry proves that larger descent statement.
