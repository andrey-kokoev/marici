# Three-provider menu: 3,658 receipt bytes, not a total optimum

Fresh `uv run --with sympy python research/voevodsky/checkers/check_fixed_menu_provider_bundles.py` bootstraps three independent owner-verified sessions of the SAME rank-one migration. They retain verified full-segment coverage: A is an archive-capable provider advanced by an owner-checked public `u<=3/4` query; B is a full-domain archive-capable provider; C is a full-domain archive-free lift provider. Scope is frozen to these CURRENT sessions and three tasks: (i) return an owner-verified answer bound to the *stored refined* state, (ii) lift the full interval including u=1, (iii) re-expose the original fine relation conjoined with the stored refined frame. An untouched B could formulate a separate hypothetical refined query, but has not published the corresponding advanced state or archive; it does not satisfy (i) or (iii) in this task contract.

The checker interrogates live handles, checked source lifts, fresh refined answer and archive re-exposure, then enumerates finite subsets. Receipt-field sums are A=1,921, B=1,917, C=1,737 bytes. Two providers are necessary: A is the only one with the authorized refined answer and archive, but cannot lift u=1; B or C supplies full-domain lifting. The least scalar receipt sum in this EXACT candidate menu is A+C = **3,658** versus A+B = 3,838. The cost difference is the previously measured 180-byte archive-enabled receipt delta. Removing A loses refined answer and re-exposure; equal full-domain section formulas cannot grant C archive access.

This is finite-menu receipt-snapshot minimization, not minimal physical storage: each bootstrap repeats owner checks, shared source code/proofs and heap overhead are outside the scalar; optimizer itself incurs work. Binding a task to an already published refined state and its owner grant is intentional. No universal optimizer, cross-source synthesis, or history selector is claimed.
