# Fixed-family archive authority does not attest Farkas source rows

The existing owner-controlled `ArchiveAuthority` prototype in `research/voevodsky/checkers/authority_aware_upgrade.py` admits an A/B ORIGINAL HISTORY under an event/context pair, issues a process-local token, checks both fields at resolution and permits revocation. It explicitly says it does not authenticate physical observation or implement a general migration compiler. The related Nima `FineSuccessorSession.commit_fine` holds the vault lock through validation and publication, so its scope has a meaningful atomic owner boundary; neither class accepts primitive Farkas row statements as its authority payload.

Fresh `check_existing_archive_scope_for_farkas.py` imports the actual vault and checks successful fixed-history resolution, foreign event/context refusal and post-revocation refusal. It also demonstrates the critical trap: even if local code improperly calls PRIVATE `_admit` with a Farkas-shaped digest string, resolution returns merely `A` or `B`, not independently verified source rows. Minting a matching-looking token is not a Farkas source attestation. Existing exact mathematical row proofs survive revocation; the revoked token loses future protected execution rights.

The first missing constructor is a distinct OWNER-controlled row attestation binding an independently checked primitive source statement, source identity, event and issuer capability. Before implementing any such service one must designate the owning source and its trust root; a self-signed local manifest cannot supply it. Next perform a read-only design of minimal attestation/revocation semantics and test foreign-source, stale-generation and forged-signature refusals under an explicit hypothetical trusted owner. Do not change Nima's fixed-family vault or represent its A/B token as authority over this Farkas source. Analytic S,A,R,C,G assignment remains deferred.
