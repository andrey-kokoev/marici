## Attempt lifecycle and outcome admission

The ledger is an append-only hash chain. A start reserves the declared action
cost once; each canonical action runs at most once. Pause/resume/checkpoints
retain the same nonce and consumed budget. Checkpoint and receipt hashes are
revalidated. Concurrent starts, missing prerequisite proofs, replay, budget
reset, stale evidence and changed contract/model/engine context are blocked.

Every conditional node now has explicit `++`, `+-`, `-+`, `--` routes. Each has a canonical prove action (`++`/`+-`) and reject action (`-+`/`--`). The physical-admission node is deliberately excluded from this conditional model. A proved dependency unlocks only declared proof children; a refuted dependency blocks that proposed constructive route but does not refute the child or overall target. Failed outcomes retain unresolved truth and replan. Route diagnostics separately identify component blockers, direct target blockers, target outcome, and registered reviewed alternatives. No alternative has been invented or registered yet: a component refutation explicitly calls for route design/review while leaving the target unresolved.

Shared obligations have one canonical owner/evidence identity and explicit consumers; reuse does not create duplicate truth priors. The hard-contradiction registry is currently empty because no scientifically justified incompatibility has been established. Future mutual-exclusion constraints require reviewed, source-pinned evidence and condition/renormalize joint worlds; unsupported constraints fail closed.

Outcomes retain the shared proof-attempt semantics:

- ++: admitted proof of the scoped proposition.
- -+: admitted scoped refutation.
- +-: unsuccessful proof attempt; truth unresolved.
- --: unsuccessful rejection attempt; truth unresolved.

Failed attempts update Bayesian beliefs and exhaust that action, never facts.
If no positive route remains, the policy abandons this portfolio; that does not
refute the target or prohibit a reviewed alternative construction.

Conclusive admission is theorem-specific. The first interface gate has an exact
receipt validator and automatic fresh runner. Later proof or counterexample
attempts can be started, checkpointed, paused and recorded, but need a reviewed,
pinned theorem-specific verifier receipt before ++/-+ admission. A generic pass, copied
++ label, changed verification level or old receipt nonce is insufficient. This
is the same distinction between a working research harness and an automatic
solver for every unproved conjecture.
