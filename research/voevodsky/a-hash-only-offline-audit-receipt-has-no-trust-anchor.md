# A hash-only offline audit receipt has no trust anchor

A conditional receipt interface for a past event-A audit needs at least a typed source identity, event, issuer, row digest, epoch, sequence and committed-operation kind, plus an independently trusted issuer authenticator and durable commit evidence. Fresh `check_conditional_offline_receipt.py` rejects a bare body hash, a self-asserted issuer, wrong event, missing claimed commit fields and—by default—ANY receipt with no independent issuer trust anchor. With a deliberately embedded toy HMAC key it returns only `CONDITIONALLY_VERIFIED_PAST_AUDIT`; it never grants current execution rights.

The toy's HMAC key is visible to the local checker and therefore NOT a real external issuer credential or publicly verifiable signature. Its matching `log_inclusion` object is also a locally asserted field, not a verified append-only log inclusion proof. These are explicit assumptions that a real offline verifier must replace with an independently established issuer key/authority scope and a verifiable committed event record; otherwise 'past audit happened' is not authenticated. Prospective revocation does not falsify a genuinely verified past event but removes future capability.

The next precise gate is a fork/equivocation hostile: two same-sequence, same-source receipts with different row digests should not both be accepted merely because each is internally well formed. An externally verifiable append-only commitment or owner-supplied reconciliation is necessary. Mathematical Farkas replay and analytic S,A,R,C,G mapping remain separate.
