# Compare-and-set refinement — cycle 11

## Increment

The concrete Boolean cell uses `false` for unused and `true` for consumed.
`compareAndSet` changes `false` to `true` with success and returns failure from
`true`. `abstractCellState` maps these concrete states into the prior atomic
specification.

`compareAndSet_refines_atomicStep` proves the one-step refinement square for
both concrete states. `runTwoCAS` then refines both labeled sequential orders,
so exactly one of two calls succeeds.

The hostile split read/write trace lets both sites read `false` before either
writes, producing `(true,true)`. It violates single use and has no atomic
linearization witness. This isolates atomic compare-and-set from an ordinary
non-atomic read followed by write.

An `AuthorizedCompareAndSet` carries the separate source grant needed to bind
the implementation model to the shared-linearization repair.

## Disposition

**Specialized the atomic specification with a concrete sequential CAS
transition and refinement proof.** This does not prove that any hardware or
language primitive implements the mathematical transition under its actual
memory model.

## Missing inputs

1. A concurrent operational semantics rather than enumeration of sequential
   CAS orders.
2. Hardware/language memory-order guarantees and a compiler refinement.
3. ABA, spurious failure, weak CAS, crashes, and persistent memory.
4. Real-time histories generated by the concrete implementation.
5. Binding from a named executable primitive to `AuthorizedCompareAndSet`.
