# Bend/HVM Cut-commutator search calibration

This is a known-answer calibration, not cosmological evidence.

The frozen grammar is

\[
x^a y^b(x+y)^c,
\qquad
0\leq a,b,c\leq 3.
\]

Candidates are encoded by

\[
\operatorname{code}(a,b,c)=a+4b+16c.
\]

The Bend program constructs a binary fork tree containing all 64 candidates
and compares their exact signatures at 16 positive nonsoft integer points.
For each target, its result is

\[
1000\,\#\{\text{matches}\}
+\sum\operatorname{code}(\text{matches}).
\]

Before execution, the expected output is frozen as

\[
(1000,1001,1004,1005),
\]

corresponding respectively to the unique expressions

\[
1,\quad x,\quad y,\quad xy.
\]

These are the primitive numerator and common-denominator factors in the
source-normalized commutator ratio

\[
e_3:e_5:e_6=y:x:1,
\qquad
\text{common denominator }xy.
\]

Passing this test establishes only that Bend/HVM can execute the frozen
bounded grammar and recover a known exact signature. It does not establish
cyclic sewing, canonicality, carrier incidence, or geometric provenance.

## Execution record

Environment:

- Bend `0.2.38`;
- HVM `2.0.22`;
- native Windows `run-rs` for the sequential calibration;
- standalone C generated by Bend and compiled with GCC under WSL2 for the
  parallel HVM test;
- no CUDA device or runtime.

The depth-six calibration returned

```text
Result: (1000, (1001, (1004, 1005)))
```

and therefore passed exactly.

## Hostile performance calibration

The same kernel was repeated over a depth-sixteen binary fork tree: four
searches of (2^{16}) leaves, hence (262144) candidate evaluations in
total. Each expected summary has (1024) matches, with code sums

[
0,quad 1024,quad 4096,quad 5120.
]

The generated parallel HVM/C run reported:

```text
Result: (* (* (* *)))
ITRS: 51084833
TIME: 0.71s
WALL: 0.79s
RSS: 691712 KiB
```

The `*` readback is not an admissible result: the exact summaries were
erased before readback. Larger depth-eighteen and depth-twenty runs also
erased their results while using approximately (2.6) GiB and (4.8) GiB,
respectively.

The warnings-denied optimized Rust traversal at depth sixteen returned

```text
[(1024, 0), (1024, 1024), (1024, 4096), (1024, 5120)]
WALL: 0.176348s
```

## Narrow verdict

[
oxed{
	ext{explicit HVM fork-tree materialization is rejected as the Marici
formula-search kernel on this host.}
}
]

It loses exact readback, consumes memory exponentially, and is slower than
the direct Rust traversal before including Bend-to-C compilation.

This does not reject Bend/HVM categorically. A future test would need a
predeclared compact superposition or streaming reduction that does not first
materialize the candidate tree. CUDA acceleration is untested. Until such a
representation is derived independently, Rust remains the search and
certificate engine.
